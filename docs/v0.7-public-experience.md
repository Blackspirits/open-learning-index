# v0.7 Public Experience — Architecture & UX Audit

## Decision

Build v0.7 as a **static, dependency-light public site generated from the canonical repository data**.

`data/courses.json` remains the only source of truth for published course facts.

The site may derive presentation-only values at build/runtime, but it must not introduce a second editorial datastore.

## Why this architecture

The repository is already publication-ready as data:

- canonical records are structured and validated;
- categories are registered centrally;
- Quality and Recommendation are distinct;
- access tiers are explicit;
- verification dates and review intervals are present;
- CI already enforces structural integrity.

The repository currently has:

- no frontend application;
- no package manager/framework dependency;
- no GitHub Pages deployment;
- no duplicated public-data layer.

That is a good starting point. A static site preserves the project's strongest properties: auditability, low maintenance, deterministic publishing and a very small attack/dependency surface.

## Architecture

### Source

- `data/courses.json` — canonical course facts.
- `data/categories.json` — canonical category names and freshness class.
- methodology/docs remain explanatory sources, not duplicated into course records.

### Build

Add a Python build step:

`python scripts/build_public_site.py`

The build should:

1. load and validate canonical records already accepted by repository CI;
2. filter publication-ineligible records from normal ranking surfaces;
3. derive presentation-only fields;
4. copy static frontend assets;
5. write a disposable deploy directory such as `_site/`;
6. emit deterministic output for the same repository state.

The build directory is not editorial source data and should not be maintained manually.

### Presentation-only derived values

Allowed derivations include:

- category display name from `data/categories.json`;
- Quality tier: S+, S, A+, A;
- free-access short label and explanation;
- freshness state from `last_verified`, `next_review` and current build date;
- normalized search text;
- language display labels;
- whether a course has a free provider credential;
- whether free academic credit is available;
- ranking position within a deterministic view.

These values should not be written back into `courses.json`.

## Deployment

Preferred production target: **GitHub Pages through GitHub Actions**.

Recommended flow:

```
main
  └─ validate canonical data
      └─ build static public site
          └─ upload Pages artifact
              └─ deploy
```

Deployment should happen only after the normal validator passes.

No backend, database, CMS or server process is required for v0.7.

## Information architecture

### 1. Home

Primary purpose: answer "where do I start?"

Recommended sections:

- search;
- top recommendations;
- categories;
- popular learning intents;
- pt-PT spotlight;
- free-certificate spotlight;
- methodology/access explanation;
- current publication stats.

The home page should not dump all 142+ records.

### 2. Explore all courses

The main catalogue view.

Required filters:

- search text;
- category;
- instruction language;
- level;
- access tier F0/F1/F2;
- Quality tier;
- free credential;
- free academic credit;
- active vs active archive.

Required sorts:

- Recommendation — default;
- Quality;
- recently verified;
- title.

Filter state should be represented in the URL so a view can be bookmarked/shared.

### 3. Category views

Each category gets a stable route or filter-preserving URL.

Show:

- category name;
- current number of canonical records;
- highest Recommendation courses;
- relevant levels/languages;
- archive/currentness caveats when useful.

Do not create manually maintained category copy in v0.7 unless it is derived or intentionally editorial.

### 4. Language views

Language is a first-class discovery dimension.

At minimum:

- all languages;
- pt-PT;
- target-language learning category;
- multilingual instructional variants.

A stronger English global leader must be able to coexist visibly with a high-quality pt-PT alternative.

### 5. Course detail

Every canonical course should have a stable detail route/view containing:

- title;
- provider;
- category;
- level;
- instruction language(s);
- Quality Score;
- Recommendation Score;
- free-access tier;
- certificate;
- academic credits;
- self-paced status;
- active/archive status;
- why recommended;
- last verified;
- next review;
- official course link.

Later versions may expose the seven Quality components; v0.7 can include them if the UX remains clear.

Evidence URLs belong in an expandable "Evidence" section rather than dominating the learner-facing page.

### 6. Editorial landing views

v0.7 should provide deterministic editorial views rather than manually copied lists:

- Best overall;
- Best by category;
- Best in pt-PT;
- Courses with a free credential;
- Courses with free academic credit;
- Beginner-friendly;
- Language learning.

Future learning paths can be added once there is a separate auditable representation for sequence/relationships.

## Course card semantics

A catalogue card should answer, without opening detail:

1. What is it?
2. Who provides it?
3. What topic and level?
4. In which language?
5. How strongly do we recommend it?
6. What exactly is free?
7. How recently was it checked?

Recommended visible content:

- title + provider;
- category;
- level;
- primary language;
- Recommendation Score;
- Quality Score;
- F0/F1/F2 badge with human label;
- last-verified date;
- compact `why_recommended` excerpt.

Do not display provider prestige as a badge.

## Access-tier UX

Raw codes must never be the only learner-facing explanation.

Recommended labels:

- **F0 — Full course + free credential**
- **F1 — Full assessed learning path**
- **F2 — Full teaching content**
- **F3 — Partial / preview only** (not shown in normal canonical ranking)

The UI should expose a short tooltip/details explanation linking to methodology.

## Score UX

Quality and Recommendation must remain visually distinct.

Recommendation answers:
> Which option should I choose today?

Quality answers:
> How strong is the course on its own terms?

Default catalogue ordering should use Recommendation, not Quality.

Score tiers are derived from methodology:

- S+: 9.50–10.00
- S: 9.00–9.49
- A+: 8.50–8.99
- A: 8.00–8.49

## Freshness UX

Every course should expose `last_verified`.

Recommended derived freshness labels:

- **Verified** — not within the final 30-day review window;
- **Review due soon** — next review within 30 days;
- **Review due** — date passed but within the maintenance grace window;
- **Priority re-review** — more than 30 days overdue.

The site must not silently present an overdue course as equally current.

The scheduled repository maintenance gate remains authoritative.

## Search

v0.7 does not need a search service.

Client-side normalized search over 100–150 records is more than sufficient.

Search index fields:

- title;
- provider;
- category display name;
- level;
- primary/other languages;
- `why_recommended`.

Do not search evidence URLs by default.

## Accessibility

Minimum QA:

- semantic HTML;
- keyboard-operable controls;
- visible focus;
- form labels;
- sufficient contrast;
- no colour-only meaning;
- score/access badges with text equivalents;
- responsive at phone width;
- reduced-motion safe;
- headings in logical order.

Target WCAG 2.2 AA behaviour where reasonably applicable.

## Performance

With fewer than 150 canonical records, performance should be trivial.

Targets:

- no frontend framework runtime unless justified;
- no external font dependency required;
- minimal JavaScript;
- no analytics in initial v0.7;
- no third-party search service;
- all main catalogue interactions available after one small data load.

## SEO / sharing

Use:

- meaningful document title and description;
- canonical site URL when deployment is final;
- Open Graph metadata;
- stable detail URLs where possible;
- crawlable static course/detail output if the initial client-side architecture does not provide adequate indexing.

For Gate 1/2, catalogue usefulness is more important than perfect SEO. Gate 3/4 should resolve static detail rendering if required.

## Data gaps discovered by the audit

The canonical schema is sufficient to ship v0.7.

Useful future schema improvements exist but are **not blockers**:

- explicit interface language;
- explicit subtitle languages in canonical records;
- target language for language-learning courses;
- original-vs-translation provenance;
- explicit prerequisites;
- estimated duration;
- required software/hardware/account friction;
- structured learner role;
- explicit learning-path relationships.

Do not delay v0.7 to redesign the data model wholesale.

Any future field must enter the canonical schema and validation process, not live only in frontend code.

## Definition of done for v0.7

v0.7 is complete when:

1. the public site is generated solely from validated repository data;
2. all publication-eligible canonical courses are represented exactly once in the main catalogue;
3. learners can search/filter by topic, language, level and free-access model;
4. Quality and Recommendation are explained and displayed separately;
5. free-access claims are understandable without reading project internals;
6. last verification is visible;
7. the site passes repository CI and deployment is deterministic;
8. no manual frontend list can drift from `data/courses.json`;
9. GitHub Pages serves the current `main` publication state;
10. maintenance in #91 can change canonical data and have the public site update from the same source automatically.

## Product judgement

The project should **not** spend the next cycle finding enough courses to reach 150.

At 142 canonical records, additional admissions should be replacement/gap driven.

The highest-value work is now making the existing evidence and curation usable by learners.


## GitHub Pages deployment prerequisite

The production workflow is prepared to use the current official GitHub Pages Actions pattern.

Before merging the deployment workflow, repository administration must set:

**Settings → Pages → Build and deployment → Source → GitHub Actions**

This repository-level Pages setting cannot be changed through the GitHub integration used by this project session.

Once enabled, the deployment workflow:

1. runs only from `main` changes relevant to the public site or via manual dispatch;
2. builds `_site/` from the canonical data;
3. uploads only the generated public artefact;
4. deploys through the protected `github-pages` environment;
5. uses no persistent `gh-pages` branch and no committed generated output.

Current action versions selected from official GitHub documentation/repositories as of 2026-09-14:

- `actions/checkout@v7`;
- `actions/setup-python@v7`;
- `actions/configure-pages@v5`;
- `actions/upload-pages-artifact@v4`;
- `actions/deploy-pages@v4`.

Do not merge the deployment workflow before Pages is configured for GitHub Actions, because a known deployment blocker should not be introduced into `main`.
